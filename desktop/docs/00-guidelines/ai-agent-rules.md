# AI 协作规范

> 状态：已生效 | 最后更新：2026-10-15 | 适用：所有 AI 编码助手（Claude Code / Copilot / Codex / 其它）

---

## 1. 定位

AI 在本项目中是**执行者**，不是决策者。人负责目标、边界与验收；AI 负责检索、起草、实现、自检。

## 2. 每次任务的开场顺序（强制）

1. 读 [docs/README.md](../README.md) 与相关 `00-guidelines` 文档。
2. 读与任务相关的领域文档（产品 -> 架构 -> 具体模块）。
3. 读真实代码，确认现状与文档一致；**不一致时先报告，不要自行假设哪边对**。
4. 列出计划（改哪些文件、为什么），再动手。

## 3. 权限边界

| 可以做 | 需要人确认 | 不允许 |
| --- | --- | --- |
| 阅读全部代码与文档 | 新增第三方依赖 | 提交任何密钥、令牌、真实邮件 |
| 修改 `internal/**`、`frontend/src/**` | 数据库 schema 迁移 | 修改 `master` 保护分支配置 |
| 新增/更新测试 | 修改 CI 与发布脚本 | 强制推送、重写已推送历史 |
| 新增/更新文档 | 删除公开 API 或绑定方法 | 以"测试需要"为由绕过校验 |
| 运行 lint / test / build | 调整产品行为与文案语义 | 关闭或跳过失败的测试 |

## 4. 必须如实报告的六件事

1. 改了哪些文件（路径 + 一句话说明）。
2. 哪些验证真的跑了、哪些**没跑**（跑不了的说明原因，不写"应该没问题"）。
3. 与文档冲突、与现有代码风格冲突之处。
4. 引入的 TODO / 占位 / 降级实现，及它们的位置。
5. 未验证的假设（例如"假定 IMAP 服务器支持 IDLE"）。
6. 潜在破坏性影响（数据格式、绑定签名、用户配置）。

## 5. 质量红线

- 不写"看起来能跑"的代码：新增分支必须有对应测试或明确说明未覆盖。
- 不编造 API/字段名；拿不到就写 `TODO(owner)` 并说明。
- 不复制粘贴大段代码凑实现；能复用则复用，不能复用要说明差异。
- 不在未阅读文件的情况下声称已修改或已检查。
- 修复缺陷时，先写能复现的失败测试，再修复。

## 6. 上下文与规模

- 单次任务改动控制在 **≤ 10 个文件 / ≤ 600 行**；超出则拆分成多步，逐步验证。
- 大范围重构前，先在 [07-tasks/active](../07-tasks/active) 建任务文档，写清步骤与回滚点。
- 涉及跨层（domain -> repository -> service -> bridge -> UI）的改动，逐层完成并逐层验证。

## 7. 输出格式

- 中文回复；代码、标识符、命令保持原文。
- 结论先行，随后证据（文件路径:行号、命令输出）。
- 不使用"我觉得""可能大概"；不确定就写"未验证"。

## 8. 提示词模板（可复制）

```text
任务：<一句话目标>

上下文：
- 相关文档：<路径>
- 相关代码：<路径>
- 约束：<规范条目 / 不得改动范围>

完成标准：
- [ ] <可验证条件 1>
- [ ] <可验证条件 2>

请先输出执行计划，确认后再改代码。
```

## 9. 事故处理

AI 产出导致构建失败或数据损坏时：

1. 回滚到上一个可用提交（`git revert`）。
2. 在 [08-history/retrospectives](../08-history/retrospectives) 记一条：触发条件、缺失的验证、增加的防线。
3. 把新防线写成本规范的一条（编号追加），而不是口头提醒。

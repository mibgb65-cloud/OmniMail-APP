## 1. 编号与文件

`BUG-YYYYMMDD-NN`，一天内按发现顺序编号。每条缺陷一个文件：
`bug-reports/BUG-20261015-01.md`。已修复的保留在目录中（不删除），状态改为 `已关闭`。

## 3. 级别定义

| 级别 | 判定 | 处理 |
| --- | --- | --- |
| P0 | 数据丢失/损坏、崩溃、无法启动、凭据泄露、安全漏洞 | 立即修复，阻断发布 |
| P1 | 核心功能不可用（收发/同步/搜索完全失效），且无绕行方案 | 当迭代修复 |
| P2 | 功能可用但有明显缺陷，或体验显著受损 | 排入下个迭代 |
| P3 | 文案、样式细节、极端场景 | 随版本处理 |

## 4. 流程

```
发现 → 建档（复现步骤齐全） → 确认（QA + 开发） → 修复（先写失败测试）
     → 待验证（提供修复提交与回归用例） → 验证 → 已关闭
```

- 建档时**必须**能复现或提供足够证据；无法复现的标记 `需要信息` 并 7 天后关闭。
- 修复后必须补回归用例，用例编号写入缺陷文件。
- P0/P1 缺陷需在 [changelog](../../08-history/changelog.md) 中记录。

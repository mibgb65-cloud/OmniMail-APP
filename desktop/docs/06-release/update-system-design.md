# 发布、安装、自动更新与消息集成设计

> 状态：分阶段实施；Windows 安装发布链路已落地，应用内更新未启用
> 日期：2026-11-01 | 关联：[TASK-0083](../07-tasks/active/TASK-0083-release-update-design.md)
> 基线：[当前构建](build.md) · [设置页](../03-design/pages/settings.md)

本文保留完整目标与原设计背景。2026-11-01 用户已确认 Windows x64、当前用户安装和 Inno Setup，
对应安装器、签名脚本、可信清单与 Actions 配置的实际操作见 [Windows 安装发布](windows-installer.md)。
本地开发安装链路与安全拒绝测试不等于正式签名或远端 CI 通过；应用内更新、设置/消息集成仍未启用。
下文未在实际操作手册标为已实现的行为仍属于后续设计，不能当作可调用接口。

## 1. 目标与建议范围

将整条链路连通，而不是仅增加一个更新按钮：

```text
推送受保护 tag
→ 检查与正式构建
→ 签名主程序/升级助手
→ 构建并签名安装包
→ 生成带签名的更新清单
→ 上传完整资产后发布 GitHub Release
→ 客户端检查、下载、验证
→ 消息中提示已就绪
→ 用户点击重启并更新
→ 正常退出、静默覆盖程序、重新启动
```

已确认首期 Windows amd64、稳定版、仅当前用户安装；macOS/Linux 保持明确不支持自动安装，
不得用 Windows exe 或假按钮冒充跨平台更新。
安装器已按确认采用 Inno Setup 6.7.0，锁定具体工具版本和下载校验值；不沿用历史 Wails v2 打包命令。

## 2. 已确定项与建议默认值

| 项目 | 来源/建议 |
| --- | --- |
| GitHub tag 自动触发构建 | 用户明确要求 |
| OmniMail 自签名 | 用户明确要求；不承诺消除 SmartScreen/未知发布者警告 |
| 安装首先选择语言 | 用户明确要求；首期简体中文、英文 |
| 数据放在用户选择的位置 | 用户明确要求，不能把附件/数据库等大数据留在 C 盘 |
| 创建桌面快捷方式 | 用户明确要求，默认勾选 |
| 安装完成后启动应用 | 建议解释为独立选项，默认不勾选，与开机自启分开 |
| Windows 登录时自动启动 | 用户要求通用设置提供，建议默认关闭 |
| 启动后自动检查更新 | 建议默认开启：启动约 15 秒后，随后每 6 小时 |
| 发现新版本自动下载 | 提供开关，建议默认关闭，避免默认占用流量 |
| 开发运行自动下载 | 用户明确禁止；Go 后端强制禁止，不能只禁用 UI |
| 自动安装 | 不自动执行；只有用户点击“重启并更新”后才静默安装 |
| 首期稳定通道 | 建议忽略 draft/prerelease，不自动降级 |

当前安装链路不静默回退，用户明确选择系统盘时告警并二次确认；静默首次安装另需显式 `/ALLOWC=1`。

## 3. 首次安装与数据位置

### 安装顺序

1. 语言选择（影响安装器与首次应用语言）。
2. 选择数据目录，明确展示数据库、附件、索引、配置、日志、缓存和更新文件均在此处。
3. 选择程序安装目录，验证当前用户可写，与数据目录分离。
4. 展示安装摘要，确认路径与所需空间。
5. 安装。
6. 完成页：创建桌面快捷方式默认勾选；安装完成后启动默认不勾选。

“安装后立即启动”和“下次登录 Windows 自启”必须用不同文案与状态，避免用户混淆。
若用户所说的安装页“自动启动”指开机自启，应在确认后改为该项；不在未确认时默认开启。

### 数据根目录建议

```text
<用户所选数据目录>/
  omnimail.db、WAL/SHM
  attachments/
  logs/
  backups/
  webview/                 # WebView profile、缓存和现有 localStorage
  updates/                 # 下载、临时包、升级任务、有限历史
  translations/            # 已实现的邮件翻译派生缓存
  已有关闭偏好、自定义服务商及新增应用偏好
```

- 不假设每台机器都有 D 盘；不默认选择磁盘根、Program Files、任意用户现有文件夹。
- 推荐非系统盘且当前用户可写的专用目录；只支持适合本地 SQLite 的本地路径，
  网络路径、重解析点、权限与目录身份需验证，不能直接信任安装器参数。
- `Config.DataDir` 必须在日志、数据库、Wails 和更新服务初始化之前解析。
- 建议解析优先级：显式 `OMNIMAIL_DATA_DIR`（含已有开发隔离）→ 当前用户安装登记；
  未安装的旧独立程序另走兼容路径。已登记但路径失效不能回落旧目录，新的安装必须完成数据选择。
- 程序和数据不能使用相同/相互包含目录，避免卸载、覆盖程序或更新清理顺带删除用户数据。
- 安装记录使用少量 HKCU 注册表元数据定位安装/数据目录；这不存放邮件大数据。
  已安装路径失效时报告错误，不静默回退 AppData 创建第二份空库。
- 必须显式配置 Wails 的 `Windows.WebviewUserDataPath`；否则前端偏好和 WebView 缓存仍可能在旧目录。
- 系统凭据管理器继续保管密码/令牌，不为“所有数据同目录”而导出明文凭据。
  Windows 注册表、系统凭据库及系统管理的 WebView2 Runtime 不属于可全部搬移的应用普通文件。
- 应用自己的 WebView 用户数据全部走所选目录；不能因此承诺 Windows 系统组件绝不占用 C 盘。
- 现有用户迁移时先退出并备份，再复制校验、切换定位记录；不能在 SQLite/WebView profile 仍被占用时盲搬。
  新目录可用和迁移成功前保留旧数据，清理旧副本需另行明确授权。
- 静默升级必须保留原程序/数据位置、语言、快捷方式和自启选择，不重新弹路径向导或重置偏好。
- 安装语言作为首次启动的初始语言；既有用户升级保留应用内选择，不能被安装器语言覆盖。
- 卸载默认保留邮件数据，不把安装目录卸载扩展成递归删除用户数据。

## 4. 签名与可信更新

### 两种职责必须区分

1. **Authenticode 自签名**：主程序、升级助手和安装包签名为 OmniMail。
   使用一次生成、持续保存的证书，不能每次 tag 随机生成新身份。
2. **更新清单签名**：建议独立 Ed25519 密钥，客户端内置可信公钥验证清单；
   清单包含安装包 SHA-256、长度、版本、架构和来源。

自签名不等于被 Windows 公共信任。不能自动导入系统根证书、
关闭签名检查或规避 UAC/SmartScreen 来换取“静默”。
清单签名与哈希是更新器的可信依据；自签名的 `UntrustedRoot` 不是 Windows 公信任证明，
也不能单凭任意 `UnknownError` 放行。当前打包在原生文件验证、预期指纹和时间戳门禁后，
仅允许预期自签身份的精确 `CERT_E_UNTRUSTEDROOT`，不要求安装根证书。
代码签名应包含受信时间戳，签名/时间戳验证不通过时停止发布，不将其降级为可忽略提示。

### 密钥保管

- PFX、私钥、口令不得进入仓库、构建日志、应用安装包或前端资源。
- 公钥/证书公开部分可随代码发布；签名私钥放受保护的 GitHub Secrets/Environment。
- 建议 Secret 职责为：PFX 内容、PFX 口令、更新清单私钥。这里只定义职责，不预填或创建值。
- 签名 job 只在受保护 tag 的可信源码上运行，不在未信任 PR 上提供密钥。
- 清单按固定域分隔前缀加原始 UTF-8 字节签名，客户端先验证，再按版本化协议解析；
  不依赖双方重新序列化 JSON 的空格/字段顺序。
- 公钥轮换必须有已有信任链授权的过渡发布；首次上线和密钥泄漏后的恢复另设明确流程，
  不接受 Release 随包提供的任意新公钥。

### 客户端校验顺序

1. 固定仓库、HTTPS、稳定版 tag/版本与平台架构。
2. 限制元数据、日志和清单大小，严格解析 SemVer、字段类型和边界。
3. 用内置信任公钥校验清单签名，再确认产品、仓库、版本、资产名、架构一致。
4. 下载到所选数据目录的 `.part` 文件，限制大小、重定向来源、超时和剩余空间。
5. 校验完整长度及 SHA-256，通过后原子标记为 ready，才显示重启按钮。
6. 安装前助手再次验证签名与包哈希，不能只依赖上一次检查。

仅从同一 Release 下载 `SHA256SUMS` 再比较不够；它可以被一起替换，必须有受信签名。
GitHub/CDN 重定向需实施时明确白名单，不允许任意 URL、本机/脚本 URL 或从前端传入执行路径。
不向跨主机重定向泄漏授权头；首期默认使用公开可读 Release，不把 PAT 内置进客户端。

## 5. GitHub Actions 发布方案

- 当前代码远端为 `mibgb65-cloud/OmniMail-APP`；公开可读性、本轮签名材料均待确认。
- tag 采用严格 `vX.Y.Z`，校验后再用作参数；只读构建 job 与有发布权限 job 分离。
- 使用锁定 Go/Node/依赖及同一 `verify`；不能另写一套放宽质量门禁的发布构建。
- 从 tag 注入 `bridge.Version`、commit、build time，以及 EXE 资源的四段式版本；
  不再把正式包发布成 `0.1.0-dev` 或静态 `0.1.0.0`。
- 正式构建需明确 release 构建标识、仓库与更新公钥；不能仅凭 `production` 标签判断正式版，
  因为当前 verify 也使用该标签。
- 先签主程序/助手，再生成并签安装包，最后计算哈希并签清单。
- 所有资产上传和必要校验完成后再发布 Release；不覆盖已发布版本/tag，
  失败不发布只有部分资产的“可更新版本”。
- Actions/工具版本和权限配置在实施阶段固定；未配置签名材料应使发布失败，而非降级 unsigned。
- 一般 push 不发布，只推 tag 发布；用户仍自己决定何时打 tag。

建议资产：对应版本的 Windows amd64 安装包、版本化更新清单、清单签名与人工校验和。
确切文件名和安装器 AppId 在首次实现时定稿，发布后保持兼容。

## 6. 更新服务与状态

Go 侧一个进程级 UpdateService，负责检查、调度、下载、验证和可安装状态；
React 设置页和消息铃铛只订阅同一份快照，不各自开启计时器或下载任务。
前端先订阅再读取快照，主窗口恢复/重新显示时再次读取，不能假设后台隐藏时的事件必定已经送达。
重启后恢复下载状态也必须重新验证本地文件，不能仅凭状态 JSON 就提供安装动作。

```text
idle → checking → upToDate / available / checkFailed
available → downloading → verifying → ready / downloadFailed
ready → preparingRestart → installing（外部助手）→ installed / installFailed
```

- 自动检查：建议启动后 15 秒，之后每 6 小时；不阻塞启动、邮件同步或正文读取。
- 手动检查仍可用。关闭自动检查只停止自动调度，不代表禁止手动检查。
- 自动下载仅在发现有效新版本时生效；关闭自动检查后，手动检查发现新版也可按下载开关处理。
- 建议自动下载默认关闭；开发运行后端强制不自动下载，不替换开发目录。
  开发版可查看版本/日志、手动检查；安装与自启能力以真实构建/安装能力控制。
- 检查合并并发请求、使用条件缓存与限流/超时处理；网络失败不宣称“已是最新版本”。
- 只运行一个下载，显示真实已传字节和总长度；断网、空间不足、签名不符均保留可重试的安全状态。
- 自动下载关闭时，不擅自删除已经完整校验的 ready 包；未完成自动任务的取消策略需明确实施。
- 偏好保存失败不假装保存成功。配置值与开发环境下的有效能力要区分，不让开关看似能绕过保护。

## 7. 更新页与消息页 UI

### 软件更新设置

- 顶部：实际安装版本、正式/开发标识、检查更新按钮、最后成功检查时间。
- 偏好区两行开关：启动后自动检查更新、发现新版本后自动下载并校验。
- 状态卡：发现版本/发布日期/说明、下载与实际进度、验证中、已就绪或失败重试。
- ready 时提供“重启并更新”；设置页和通知卡共用同一操作及禁用门禁。
- 单独显示“当前版本更新日志”，来自当前包内嵌的发布说明，离线可读。
  新版本说明必须标为“新版本更新说明”，不能把 latest Release body 冒充当前日志。
- Release 外部文本按不可信内容处理，先用安全纯文本/受限展示，不执行 HTML；
  仅提供校验后的固定 GitHub 发布页链接。

### 消息铃铛

- 无更新、无待处理事项时保留现有空态。
- 有新版本时显示一张更新卡：版本、状态、查看更新/下载。
- 下载验证完成后卡片主按钮为“重启并更新”，不是伪装成已安装。
- 同一版本和状态去重；打开消息可清未读标记，但不销毁已下载的包。
- 自动轮询无变化时不反复刷通知；失败仅在需要用户处理时展示可重试状态。
- 这是应用内消息，不代表已经实现 Windows 新邮件 Toast；设置中的系统通知能力边界要同步写清。

## 8. 重启与静默安装

1. Go 确认仍是同一 ready 版本；IPC 不接受任意包路径或命令。
2. 有未保存撰写内容、发送中或发送结果不确定时先阻止/引导处理，不静默丢弃或自动重发邮件。
3. 写入私有升级任务，启动受信升级助手，之后正常关闭邮件服务和应用。
4. 退出采用明确 Quit，绕过现有“关闭窗口留后台/每次询问”的偏好，不重复询问关闭方式。
5. 助手等待准确的父进程身份/句柄退出，再次验证缓存与信任签名，运行安装器静默模式。
6. 静默模式复用既有 AppId/路径/语言/快捷方式/自启设置，不自动清用户数据，不强制重启 Windows。
7. 成功后以原普通用户身份打开新应用，报告实际结果；失败保留可诊断状态，不能显示升级成功。

建议当前用户安装使程序目录可写，从而避免普通升级需要提权。
若安装位置需要管理员权限，不能承诺完全无系统提示，更不能通过 UAC 绕过实现。
“静默”指不重复出现安装向导，不代表跳过安全确认和权限机制。

助手应在受保护的更新缓存运行副本，不在自身正被覆盖的安装路径执行。
路径/重解析点、包替换的 TOCTOU、任务文件权限和进程身份必须校验；不枚举并终止所有 WebView/Edge 进程。
安装失败优先保留旧程序和数据；数据库迁移后不能承诺任意降级回旧程序，
须基于匹配备份和 schema 边界恢复，而不是把旧 EXE 强行放回新库。

## 9. 通用设置中的开机自启

- 当前用户的 Windows 登录自启，默认关闭；安装完成立即启动是另一项设置。
- 使用当前用户启动注册信息；只构造已验证安装程序的固定命令，不接收前端传入的可执行路径。
- 界面从系统真实读取状态，写入失败保留旧状态；不靠 JSON 布尔值假装已经注册成功。
- 更新后指向稳定安装路径，不指向 `.task`、下载临时目录或开发运行路径。
- 登录启动建议保留在后台，有托盘可恢复；开发/未安装运行不创建自启项。
- 卸载移除本应用拥有的自启项，不误删其他启动项。

## 10. 实施分期与验收

| 阶段 | 闭环产出 | 关键验收 |
| --- | --- | --- |
| A | 数据定位、WebView profile、语言与自启平台能力 | 全新安装/既有路径、盘不可用不回退 C、真实自启开关和开发禁用 |
| B | 正式版本注入、自签名、安装器和 tag workflow | 语言顺序、数据位置、快捷方式/启动默认值、证书/私钥不泄漏、实际 tag 构建 |
| C | 签名清单、检查/下载/验证与偏好调度 | SemVer、恶意清单/重定向/坏哈希/中断/并发、开发不自动下载 |
| D | 更新页、当前日志、消息卡和重启助手 | 两处状态一致、保护发送/编辑、静默安装后重启与失败恢复 |

每阶段继续按仓库规则拆为最多 10 文件/600 行的小步骤，重要实现运行统一 verify。
发布与安装能力还需 Windows VM/实机安装、真实 GitHub Release 和系统权限测试；
mock、浏览器预览与本地构建都不能代替完整升级验收。

## 11. 实施前待确认

1. 是否接受 Windows amd64 首期、当前用户安装及 Inno Setup 工具选择。
2. 安装完成的“自动启动”是立即运行还是开机自启；本提案建议区分，二者都默认关闭。
3. 是否接受自动检查默认开、每 6 小时、自动下载默认关的建议。
4. 只有 C 盘时是否允许明确告警并由用户二次确认；无论如何不静默回退。
5. Release 是否公开可读；若私有，另设计认证/公共分发，不能在应用内嵌 PAT。
6. 自签名证书和更新签名密钥由用户提供，还是另行授权在安全位置生成并配置 GitHub Secrets。

上述未确认项不预填成用户既定要求。本轮只完成设计，未触发发布、安装、自启注册或下载更新。

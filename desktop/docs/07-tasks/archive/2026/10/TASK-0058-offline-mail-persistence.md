# TASK-0058 后台同步完整正文并持久保存数据库

> 状态：已完成
> 负责人：@Codex | 创建：2026-10-31 | 优先级：P1

## 用户需求与范围

- 用户要求所有邮件内容保存在本地数据库，而不是仅有可丢弃缓存；图片可以采用缓存。
- 当前已下载正文以 SQLite 的 `body_text`、`body_html`、`body_version` 持久保存，但后台只同步邮件头，
  未打开邮件通常没有正文。修复这一缺口：正常同步自动分批下载受支持邮件的完整正文，已有摘要记录自动补齐。
- 图片与附件继续采用现有内容寻址文件和数据库引用，不自动访问 HTML 外部图片；不下载未知远程资源。
- 不包含：原始 EML 永久归档、改写服务器删除/UIDVALIDITY 重置语义、无限制超大邮件、
  明文日志/聊天读取用户正文、依赖/数据库迁移、自动提交或推送。

## 当前事实与方案取舍

- 初始工作树存在 TASK-0056/0057 未提交改动，保留全部现有功能及记录。
- `SaveMailBody` 已事务保存文字和 HTML；关闭重开数据库可恢复，字段 Cached 表示本地正文已具备，不代表内存缓存。
- 现有 `cacheMessage` 仅在打开/显式重新获取时下载正文，后台 `syncPass` 只调用 `SaveMailBatch`。
- 方案 A：同步每封使用新连接调用前台读取，简单但会与用户阅读争用前台额度并反复认证。
  方案 B（采用）：复用后台只读会话、既有 MIME/附件事务管道，按限额补齐待保存正文，保留前台独立通道。
- 新增内部仓储待补正文查询，不新增表/字段/迁移，不改变 IPC；正文成功落库才从待办消失。
  以数据库状态恢复进度，避免依赖内存“已下载”假设；旧版只有文字的正文可升级为当前版本。
- 每轮遵守原有时间预算与有限批次；正文失败/超限明确保留未完成状态，不标记假同步成功。
  使用 BODY.PEEK，不因后台下载标为已读；真正展示后的自动已读行为不变。
- 实施细化：已有待补正文优先处理，再推进邮件头；新邮件头发现待补正文时续排，不把“摘要同步完成”当作完整正文完成。
  单连接限制正文数量与累计预估字节，避免复用会话时触碰现有 64 MiB 总读取保护；从 SQLite 待办状态断点恢复。
- 现有 ADR-0002 含“超过 1 MiB 正文外置”的历史目标，当前实现实际拒绝超预算正文；本轮不扩大解码安全上限，
  不对超限邮件宣称完整保存，补充当前行为的决策记录与限制。

## 实现与限制

- `MailBodyTarget` 与参数化待办查询只读取同账号/文件夹/UIDVALIDITY 下缺失或旧版正文，
  以成功 SQLite 事务消除待办；无需迁移或新的 IPC 字段。
- 后台使用既有只读会话和 `storeMessageBody` 管道，保存文字、原始 HTML 及附件引用；
  每连接有数量、预估字节、邮件头及软时间预算，超出预算续排，未完成正文不会被标为完整周期结束。
- `Cached` 既有字段仅指“数据库已具备正文”，不是正文放在易失缓存或附件目录。没有新增正文文件或自动过期清理。
- 真实开发应用 12:43:00 载入最终代码后，Gmail 连续输出 `SYNC_PROGRESS`，正在补齐历史正文；
  没有读取用户数据库正文来审计数量，不能宣称当前所有历史内容均已下载完成。
- 同时捕获 QQ `persist_body / MAIL_PROTOCOL_FAILED / response_parse` 和网易 163 SELECT 错误，
  已交回 TASK-0037；这些账号不记为全量离线成功，不静默跳过或篡改成功状态。
- 解码文字总量仍上限 1 MiB，原始 MIME 40 MiB、单附件 25 MiB；超限不截断伪装完整。支持更大正文需另行评估数据库约束与安全预算。
- 保留远端删除镜像、UIDVALIDITY 重建和账号物理删除行为；这是本地持久化而非永不删除的备份/归档。
- 新增 ADR-0008 为实现待评审草稿，明确与历史 ADR-0002 目标差异；未伪造架构批准、race、macOS 或全部服务商验收。

## 1. 目录含义

| 路径 | 内容 | 谁能写 |
| --- | --- | --- |
| [backlog.md](backlog.md) | 未排期的任务池（含想法、技术债、缺陷） | 所有人 |
| `active/` | 当前迭代进行中的任务（每个任务一个文件） | 认领人 |
| `archive/2026/10/` | 已完成/已取消任务的归档（按年月） | 完成时移动 |

## 2. 任务状态

```
待排期(backlog) → 已计划(active，状态:待开始) → 进行中 → 待评审 → 已完成 → 归档
                                                    ↘ 已取消（写明原因）
```

## 3. 任务文件模板

文件名：`active/TASK-<4位序号>-<slug>.md`

```markdown
# TASK-0001 任务标题

> 状态：待开始 | 进行中 | 待评审 | 已完成 | 已取消
> 负责人：@xxx | 创建：YYYY-MM-DD | 预计：N 天 | 优先级：P0/P1/P2
> 关联：FR-xx / FEAT-xxxx / ADR-xxxx / BUG-xxxxxx-xx

## 目标
一句话说明完成后世界有什么不同（可验证）。

## 范围
### 包含
- ...
### 不包含
- ...

## 实现步骤
1. [ ] ...
2. [ ] ...

## 验收标准
- [ ] 可测试的条件 1
- [ ] 可测试的条件 2

## 风险与依赖
- ...

## 验证记录
| 日期 | 验证内容 | 结果 |
| --- | --- | --- |

## 完成记录
- 提交：`<sha>`
- 文档更新：<链接>
- 归档日期：
```

## 4. 工作流规则

1. **单一负责人**：一个任务一个 owner，不写"大家一起"。
2. **一个任务 ≤ 3 天**：超出必须拆分；拆出来的写进 backlog。
3. **验收标准先写**：没有可测试验收标准的任务不进 `active/`。
4. **每日更新**：勾选步骤、更新状态，不写"已推进"。
5. **完成任务时**：更新文档 -> 移动文件到 `archive/YYYY/MM/` -> 在 [changelog](../08-history/changelog.md) 记录（若影响用户）。
6. **取消任务**：保留文件并写明原因与替代方案，不删除。

## 5. 优先级定义

| 优先级 | 含义 | 进入迭代 |
| --- | --- | --- |
| P0 | 阻塞发布或数据安全 | 立即 |
| P1 | 当前里程碑必须 | 本迭代 |
| P2 | 有价值但可延后 | 下迭代或视容量 |
| P3 | 想法/优化 | backlog 长期 |

## 6. 迭代节奏

- 周期：1 周（周一计划，周五回顾）。
- 容量：`团队成员数 × 4 天`（预留 1 天处理中断）。
- 计划会产出：本迭代 `active/` 任务文件 + 明确的"不做什么"。
- 回顾产出：[08-history/retrospectives](../08-history/retrospectives/)。

## 7. 与代码的关系

| 动作 | 要求 |
| --- | --- |
| 开分支 | 分支名与任务编号对应（`feat/TASK-0001-mail-pagination`） |
| PR | 描述首行写 `TASK-xxxx`，便于追溯 |
| 合并 | 任务文件中的勾选项同步更新 |
| 发布 | 归档目录 `archive/YYYY/MM/` 即该版本的交付清单 |

## 1. 适用范围与事实来源

任何开发任务，不论大小，在修改代码、配置、文档或其他项目文件前，必须先创建或复用
Task Record。首次创建该记录本身是引导例外，不需要再创建一份“记录的记录”。
只读答疑、检索和评估不需要任务记录；一旦转为修改，先补齐记录再实施。

- 任务文件记录真实历史，是需求、分析、实施、验证和 Git 处置的事实来源。
- `active/README.md` 只维护当前任务摘要，不复制完整验证结果。
- 同一目标的连续调整可复用既有任务，但每轮先更新需求、计划和验证范围；不同目标另建任务。
- 不事后补造成事前记录，不倒填日期，不伪造命令结果、审批或提交号。

## 2. 目录、编号与状态

| 路径 | 内容 | 谁能写 |
| --- | --- | --- |
| [backlog.md](backlog.md) | 未排期的任务池（含想法、技术债、缺陷） | 所有人 |
| `active/` | 当前迭代进行中的任务（每个任务一个文件） | 认领人 |
| `archive/YYYY/MM/` | 已完成/已取消任务的历史记录 | 满足结案条件后移动 |

编号先检查 active 与 archive 中已有 `TASK-xxxx`，选择下一个未使用编号，不覆盖现有文件。
默认仓库级开发任务也记录在此处，直到其他平台建立并明确自己的任务规范。

```
需求 → 待开始（Planned）→ 进行中（In Progress）→ 待评审 → 已完成 → 归档
                                 ↘ 已取消（记录原因后归档）
```

- **待开始**：记录已存在，目标、范围、计划和验收可检查，尚未修改其他项目文件。
- **进行中**：已完成必要分析，正在实施或验证。
- **待评审**：实现及实际验证结果已回填，等待用户评审、提交授权或其他结案确认；不表示已提交。
- **已完成**：验收、文档、风险说明和 Git 处置均明确，并满足下述结案条件。
- **已取消**：保留已做工作、原因、替代方案及 Git 状态，不直接删除记录。

## 3. 标准流程

1. 检查工作树与任务索引，区分本任务和既有用户改动。
2. 创建或复用 `active/TASK-<4位序号>-<英文slug>.md`，写需求与目标，状态为待开始。
3. 阅读相关文档与代码，填写分析、包含/不包含范围、待确认项、实施计划及可测试验收标准。
4. 状态改为进行中，再实施其他文件修改；小步验证，修复缺陷先复现失败测试。
5. 按根目录 AGENTS.md 选择验证范围；重要代码、接口、依赖及构建变更运行完整 verify。
6. 更新受影响文档、审阅本任务差异和新增文件，回填实际实现结果与验证结果。
7. 写明 Git 处置并交付评审；未经明确授权不提交、推送或清理工作树。
8. 满足结案条件后改为已完成，移动到实际归档日期的 `archive/YYYY/MM/`，更新索引。

小任务可以使用精简记录，但至少包含需求/范围、分析计划、实际实现、验证、Git 处置及遗留风险。
不要为了凑模板虚构需求、风险或测试；尚未执行的字段明确写“未执行”，不是“通过”。

## 4. 任务记录模板

```markdown
# TASK-0001 任务标题

> 状态：待开始 | 进行中 | 待评审 | 已完成 | 已取消
> 负责人：@xxx | 创建：YYYY-MM-DD | 预计：N 天 | 优先级：P0/P1/P2
> 关联：FR-xx / FEAT-xxxx / ADR-xxxx / BUG-xxxxxx-xx

## 需求与目标
用户要求和可验证目标；未确定的信息写待确认，不补造产品需求。

## 范围
### 包含
- ...
### 不包含
- ...

## 分析
- 当前代码与文档的事实、差异、影响范围、候选方案及取舍。
- 用户既有改动与不得触碰的范围。

## 实施计划
1. [ ] ...
2. [ ] ...

## 验收标准
- [ ] 可测试的条件 1
- [ ] 可测试的条件 2

## 风险与依赖
- ...

## 实现结果
实际修改、关键决策、未实现/降级部分；未开始时明确写尚未开始。

## 验证记录
| 日期 | 命令或核对项及覆盖范围 | 实际结果/失败原因 |
| --- | --- | --- |
| YYYY-MM-DD | 尚未执行 | 不得预填通过 |

## Git 与交付
- 提交/推送授权：未授权 / 已授权（分别注明）。
- 关联实现提交：未提交 / 已核对的实际 SHA。
- 用户既有改动：如何保留，是否存在无法独立暂存的混合修改。
- 遗留风险与未验证项：
- 交付状态：实施中 / 待评审 / 用户确认结案。
- 文档更新：
- 归档日期：未归档 / 实际日期。
```

## 5. 验证与结案条件

完整门禁在仓库根目录执行 `go -C desktop tool wails3 task verify`。失败时写明原因与后续处理；
修复后重跑受影响检查。验证后再次改动代码或配置时，原结果不能直接代表新状态。

只有以下条件都明确，才可结案：

1. 验收项已实现，实际结果与验证记录已填写；跳过的检查和遗留风险有理由且已交付说明。
2. 受影响文档与索引已更新，不把计划、mock、浏览器检查或本地门禁说成真实桌面能力或 CI 通过。
3. 已按授权提交并登记实际实现提交号，**或者用户明确允许以未提交状态结案**。
4. 若尚未授权提交，也未确认免提交结案，则保持待评审、留在 active，不擅自归档。

提交号应在实际提交后登记，不得提前填入。登记的是实现提交，可在后续文档提交中保存记录；
不要求任务记录包含保存它自身的提交号，也不能为追逐该哈希反复 amend。

归档时保留同一任务文件和编号，更新链接；归档目录是历史记录，不另复制一份冲突正文。
有用户可见影响时同步 [changelog](../08-history/changelog.md)。取消任务同样记录实际结果，不删除历史。

## 6. Git 安全与协作

- 一个任务一个负责人；多步骤先更新计划，不把其他任务编号借作所有改动的记录。
- 未授权不自动暂存、提交或推送。已有用户改动不得覆盖、丢弃、批量暂存或混入提交。
- 同一文件有其他任务修改时按差异块审阅；无法安全分离时请求确认，不因文件未跟踪就认领全部内容。
- PR 必须包含任务编号；具体提交与分支规则见 [Git 规范](../00-guidelines/git-conventions.md)。
- 预计超过 3 天或单步骤超过规模限制时先拆任务；迭代节奏按实际协作约定，不虚构团队成员或评审。

| 动作 | 要求 |
| --- | --- |
| 继续同一任务 | 先追加本轮需求、范围与计划，再修改文件 |
| 实施与验证 | 分别记录计划和实际结果，不把勾选计划当作证据 |
| 未提交交付 | 保持待评审，明确未提交原因 |
| 授权提交 | 审阅本任务差异，提交后登记真实实现 SHA |
| 结案与归档 | 按完成条件确认，更新当前索引和归档链接 |

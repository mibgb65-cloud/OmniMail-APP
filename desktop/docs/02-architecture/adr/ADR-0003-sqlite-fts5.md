# ADR-0003 搜索：SQLite FTS5 + 中文二元分词

> 状态：草稿 | 最后更新：2026-10-15 | 决策人：@backend-lead

## 背景

需求：跨账号全字段检索，1 万封规模 P95 ≤ 120ms，中英文混排可用，索引可增量维护、可重建。
难点在中文：FTS5 的 `unicode61` 分词器把连续中文视为一个 token，导致"季度报告"
无法被"报告"命中。

## 备选方案

### 方案 A：FTS5 + unicode61 + 应用层二元（bigram）
- 写入时把中文串切成 `季度 度报 报告` 追加到索引字段；查询时对中文查询串同样切分并用 AND/OR 组合。
- 优点：零外部依赖，纯 SQL 可维护；中文召回率高；实现可控。
- 缺点：索引体积约为中文正文的 1.5-2 倍；单字查询无法命中；精确短语需额外校验。

### 方案 B：FTS5 + 第三方中文分词（gojieba / sego）
- 优点：分词更符合语义，索引体积更小，支持更精确的打分。
- 缺点：引入 CGO 依赖（gojieba）影响交叉编译；词典维护成本；不同分词器版本导致索引需重建。

### 方案 C：外部搜索引擎（Bleve，纯 Go）
- 优点：完整倒排索引、打分与高亮能力强，支持自定义中文分析器。
- 缺点：与 SQL 过滤条件组合需两段查询再交集，一致性维护成本高；索引文件独立，备份需成对处理；
  1 万封以下规模收益不明显。

### 方案 D：不做中文分词，仅前缀匹配
- 优点：实现最简。
- 缺点：无法满足"输入词中间片段"的检索，用户预期不匹配（中文用户习惯直接输词）。

## 决策

**采用方案 A 作为 v1 基线**，并保留替换点：

- `Indexer` 接口隔离（`domain.Indexer`），实现可替换为方案 B/C 而不影响上层。
- 索引字段设计留出 `zh_tokens` 虚拟列，便于将来切换分词器时重建。
- 单字查询（长度 < 2 的中文）降级为 `LIKE '%字%'` 扫描并限制范围（当前筛选账号），
  并在 UI 标注结果可能不完整。

## 后果

- 正面：
  - 无 CGO，交叉编译简单（配合纯 Go SQLite 驱动）。
  - 中文召回满足"任意相邻二字"命中，覆盖绝大多数查询意图。
  - 索引与主库同一事务维护，不存在两库不一致。
- 负面（接受的风险）：
  - 磁盘占用增加。按 100 万封评估需实测，若超过可用预期，改为仅索引最近 2 年正文。
  - 单字与跨词边界查询效果弱。
  - 短语检索需二次校验原文，增加少量 CPU。
- 度量与触发重新评估的条件：
  - 若中文查询 "无结果但人工可找到" 的比例 > 3%（通过用户"找不到？"反馈点统计），
    切换到方案 B；若需要复杂打分/词频统计，评估方案 C。

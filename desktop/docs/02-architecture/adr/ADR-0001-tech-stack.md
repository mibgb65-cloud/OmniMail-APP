# ADR-0001 技术栈选型：Wails + Go + React

> 状态：已生效 | 最后更新：2026-10-15 | 决策人：@arch-lead

## 背景

需要跨 Windows / macOS 的桌面邮件客户端，核心矛盾：

- 邮件协议（IMAP/SMTP/MIME）实现复杂，需要成熟的库与可靠的并发/网络能力。
- 用户对体积、内存、启动速度敏感（Electron 客户端常被诟病 300MB+ 内存）。
- 团队技术栈：Go 后端 + React 前端；无 C++/Rust 桌面经验。

## 备选方案

### 方案 A：Electron + Node/Go sidecar
- 优点：生态最全，Web 技术可直接复用，调试成熟。
- 缺点：安装包 ≥ 100MB；每窗口独立渲染进程；常驻内存难以做到 250MB 以内；
  需要额外 sidecar 进程管理 Go 二进制。

### 方案 B：Wails v2（Go + 系统 WebView）
- 优点：单进程；无捆绑 Chromium，安装包可控制在 25MB 内；
  Go 原生并发适合同步引擎；绑定生成代码简单；与团队 Go 能力匹配。
- 缺点：WebView 版本差异（WebView2 / WKWebView）；平台能力需要自己封；
  社区规模小于 Electron，遇到问题需读源码。

### 方案 C：Tauri（Rust + 系统 WebView）
- 优点：体积与内存最优，安全模型清晰。
- 缺点：需要 Rust 能力；IMAP/MIME 生态弱于 Go；团队需要较大学习成本。

### 方案 D：原生（WinUI / AppKit 双实现）
- 优点：体验与性能最好。
- 缺点：等于两个产品，人力不可行。

## 决策

选 **方案 B：Wails v2 + Go 1.22+ + React 18 + TypeScript 5**。

理由：在"体积/内存"和"团队能力/生态"之间取得平衡。包体与内存可以通过
不捆绑 Chromium 一次性解决；而协议复杂性由 Go 生态承担；UI 复用团队 React 能力。

## 后果

- 正面：
  - 安装包目标 ≤ 25MB，常驻内存目标 ≤ 250MB。
  - 前后端类型可生成，减少契约漂移。
  - Go 的 `context` + goroutine 模型适配多账号同步。
- 负面（接受的风险）：
  - WebView 渲染差异需在两端回归；复杂 CSS 需测试。
  - 平台能力（托盘、通知、快捷键、钥匙串）需自行实现与维护，工作量约占总量的 15%。
  - Wails 版本升级可能带来绑定层变化，需锁定版本并单独验证。
- 触发重新评估的条件：
  - Wails 停止维护超过 12 个月；
  - 出现无法绕过的 WebView 兼容问题（如 macOS 旧版本）；
  - 需要 Linux 端支持且投入产出比成立。

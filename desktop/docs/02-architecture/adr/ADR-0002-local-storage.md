# ADR-0002 本地存储：SQLite + 文件系统

> 状态：已生效 | 最后更新：2026-10-15 | 决策人：@arch-lead

> 2026-10-31 实现核对：当前 schema v3 的受支持文字/HTML 正文写 SQLite；
> 本文“超过 1 MiB 正文外置”为未落地的历史目标，不是当前存储事实。
> 用户已要求正文自动同步并入库，当前实施与安全边界见
> [ADR-0008（实现待评审）](ADR-0008-offline-mail-bodies.md)，附件文件存储架构不变。

## 背景

需要存储：账号配置、邮件头与正文、附件、全文索引、同步游标、草稿、离线操作队列。
约束：单机、单进程、数据量可达百万封、必须支持事务与崩溃恢复、需可备份与迁移。

## 备选方案

### 方案 A：SQLite（单文件 + WAL）
- 优点：ACID；单文件易备份；FTS5 内置；Go 绑定成熟；`VACUUM INTO` 即可做一致性备份。
- 缺点：并发写单写者；大 BLOB 会让库文件膨胀；需要处理 WAL 增长。

### 方案 B：BoltDB / Badger（KV）
- 优点：纯 Go、写性能好。
- 缺点：无 SQL 查询能力，列表分页与多条件过滤需自行实现；无内置全文索引。

### 方案 C：每条邮件一个文件（Maildir 风格）+ 元数据库
- 优点：与邮件生态一致，易被外部工具接管。
- 缺点：文件数爆炸导致备份/扫描慢；跨文件事务困难；Windows 上大量小文件性能差。

### 方案 D：托管数据库（服务端）
- 与"本地优先、不经服务器"的产品前提冲突，排除。

## 决策

**方案 A**，并作两点约定：

1. **大对象外置**：附件与超过 1MB 的正文存文件系统（按 `sha256` 分桶），DB 只存引用与元数据。
2. **单写者**：所有写操作经 `repository` 层串行化（应用级互斥 + 短事务），避免 `SQLITE_BUSY`。

## 后果

- 正面：
  - 列表分页、多条件过滤、全文检索统一在 SQL 内完成。
  - 备份 = 一个文件的复制或 `VACUUM INTO`，恢复流程简单。
  - 迁移可用版本化 SQL 管理（见 [migrations](../database/migrations.md)）。
- 负面（接受的风险）：
  - 单写者限制了写入吞吐；批量写入需要攒批（200 条/事务）。
  - 附件与 DB 需保持一致性：删除邮件后才清理附件，孤儿文件由后台任务按引用计数回收。
  - Windows 下文件锁与杀毒软件扫描可能导致偶发 `busy_timeout`，已设 5s 并必须处理超时。
- 触发重新评估的条件：
  - 单库超过 5GB 或列表查询 P95 超过目标 3 倍；
  - 需要多进程共享数据（当前设计明确不支持）。

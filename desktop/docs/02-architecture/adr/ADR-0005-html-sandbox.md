# ADR-0005 邮件 HTML 渲染隔离

> 状态：草稿 | 最后更新：2026-10-15 | 决策人：@security

## 背景

邮件 HTML 来自不可信第三方，可能包含脚本、远程图片（跟踪像素）、仿冒表单、超大内联资源。
必须在"尽量还原原邮件样式"与"零代码执行、零被动跟踪"之间取平衡。

## 备选方案

### 方案 A：直接 `dangerouslySetInnerHTML` 注入主文档
- 优点：实现最快，样式最接近。
- 缺点：XSS 直接命中主上下文，可访问 `window.go` 绑定（等于把 Go 能力交给攻击者）。
  **不可接受**，排除。

### 方案 B：服务端清洗 + 沙箱 iframe + CSP
- Go 侧用白名单清洗（`bluemonday` 或自研），移除脚本类标签与事件属性；
  渲染进 `sandbox="allow-same-origin"`（**不含** `allow-scripts`）的 iframe；
  iframe 内注入 CSP `default-src 'none'`，图片仅 `data:`/`cid:`，远程资源需用户显式解锁。
- 优点：双重防线（清洗 + 浏览器隔离）；远程资源默认不加载，杜绝跟踪；
  iframe 内即便残留脚本也无法执行（无 `allow-scripts`）。
- 缺点：部分邮件样式依赖外部 CSS/字体，会降级；复杂布局可能不完美；
  需要维护清洗白名单并与 iframe 策略同步。

### 方案 C：纯文本 / 严格无格式渲染
- 优点：最安全，零维护。
- 缺点：电商、通知类邮件可读性大幅下降，用户会流失到网页邮箱。

### 方案 D：第三方渲染服务/远程代理
- 与"本地优先、不经过服务器"冲突，排除。

## 决策

**采用方案 B**，并作以下具体规定：

1. 清洗白名单见 [FEAT-0007](../../01-product/features/FEAT-0007-safe-html-render.md#白名单)，名单为唯一来源。
2. iframe 属性固定为 `sandbox="allow-same-origin"` + `referrerpolicy="no-referrer"`；
   **禁止**追加 `allow-scripts` / `allow-top-navigation` / `allow-popups`。
3. 链接重写：`href` 置为 `about:blank#omnimail-link`，真实地址存 `data-href`，
   点击由父页面校验协议白名单后交系统浏览器。
4. 远程图片默认阻止；用户解锁按"发件域"记忆，不全局放开。
5. 清洗实现选择：优先 `bluemonday`（成熟、可配置），自研仅在其无法满足
   `style` 属性白名单过滤时补充；最终选择在实现阶段定稿并追加到本 ADR。

## 后果

- 正面：
  - 攻击面收敛到"样式与布局"，不涉及脚本执行与绑定调用。
  - 默认不发起任何第三方请求，阅读行为不外泄。
  - 与主应用上下文隔离，iframe 崩溃不影响主界面。
- 负面（接受的风险）：
  - 部分营销邮件在 iframe 中显示不如网页邮箱，需提供"在浏览器中打开"入口。
  - 清洗规则与 iframe 策略需成对维护，漏配一处即退化；需回归测试用例集（见 [TC 集](../../05-testing/test-cases)）。
  - `style` 属性白名单过滤实现复杂（CSS 值需按属性再校验），存在遗漏风险。
- 触发重新评估的条件：
  - 需要支持 `<video>/<audio>` 内嵌播放；
  - 需要支持 S/MIME 签名校验后的可信渲染；
  - WebView 对 `sandbox` 属性的支持出现回归。

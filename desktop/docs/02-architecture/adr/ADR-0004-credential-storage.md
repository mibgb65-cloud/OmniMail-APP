# ADR-0004 凭据存储：系统钥匙串 + DPAPI 降级

> 实现核对（2026-10-28）：TASK-0033 已通过适配库接入系统凭据主路径，
> Windows 随机临时条目的原生读/写/删已验证。macOS 未实机验证，DPAPI 降级未实现；
> 当前不可用即明确报错、不保存账号，不静默写加密文件或明文。本文原始降级目标保留，不能据此称已落地。

> 状态：已生效 | 最后更新：2026-10-15 | 决策人：@security

## 背景

需要保存：IMAP/SMTP 密码或应用专用密码、OAuth2 access/refresh token。
约束：绝不落明文；不写日志；用户移除账号时必须一并清除；企业环境可能需要自动化部署。

## 备选方案

### 方案 A：应用自管加密文件
- 用固定密钥或口令派生密钥加密后存 JSON。
- 缺点：密钥放哪都是问题；固定密钥等于混淆；向用户索要口令会破坏体验。

### 方案 B：系统钥匙串
- Windows Credential Manager / macOS Keychain。
- 优点：由 OS 保护（与登录会话绑定）、用户可在系统设置中查看/吊销、审计友好。
- 缺点：需要平台封装；Windows 单条 blob 约 2560 字节上限；某些精简/服务账户环境不可用。

### 方案 C：数据库内加密列
- 优点：与业务数据同事务。
- 缺点：密钥管理问题同方案 A，且备份文件包含密文，泄露面更大。

## 决策

**方案 B 为主，方案 C 不采用**，并规定降级路径：

1. 主路径：`platform.Keychain` 抽象，Windows 走 Credential Manager（`wincred`），macOS 走 Keychain。
2. 数据库只存 `credential_ref`（条目名 `omnimail/account/<ACCOUNT_ID>`），不含任何密文。
3. 超出钥匙串单条上限时（如部分 OAuth 令牌组合）：拆分为 `...-auth` 与 `...-refresh` 两条。
4. 钥匙串不可用时：Windows 退回 **DPAPI**（`CryptProtectData`，当前用户作用域）加密后存
   `%APPDATA%/OmniMail/secrets/<ref>.bin`，文件 ACL 限当前用户；
   macOS 若 Keychain 不可用则**不支持保存**，要求每次启动重新授权并明确提示。
   降级状态必须写入设置页（"当前凭据保护级别：系统钥匙串 / 用户加密文件"）。

## 后果

- 正面：
  - 密文事务与业务数据解耦，备份不含凭据，导入导出安全。
  - 用户可在系统中独立吊销。
  - 移除账号流程清晰：删除 DB 行 + 删除钥匙串条目 + 清理临时文件。
- 负面（接受的风险）：
  - 平台实现与测试成本；CI 上需要 fake 实现。
  - 系统迁移/更换用户账户后凭据丢失，需要重新登录（在文档中说明）。
  - DPAPI 降级后安全性依赖用户账户隔离，需在 UI 明示。
- 触发重新评估的条件：
  - 需要支持"多设备同步账号配置"（届时凭据仍不同步，仅配置同步）；
  - 需要企业统一下发的预配置凭据。

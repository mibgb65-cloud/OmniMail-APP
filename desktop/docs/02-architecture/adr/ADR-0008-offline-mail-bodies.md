# ADR-0008 邮件正文自动同步并持久保存在 SQLite

> 状态：草稿（实现待评审） | 日期：2026-10-31 | 提议人：@Codex
> 需求依据：用户明确要求正文保存在本地数据库，图片可缓存
> 任务：[TASK-0058](../../07-tasks/active/TASK-0058-offline-mail-persistence.md)

## 背景

当前 schema v3 已有 `mail_message.body_text/body_html/body_version`，已下载正文能随数据库重开恢复；
但原后台同步只获取邮件头，正文主要由用户打开时下载。用户要求邮件内容离线持久可用，
不能将“只同步了摘要”描述为完整邮件已存本地。

## 方案比较

- 继续按需获取：网络最省，但未打开邮件离线无正文，不满足本次需求。
- 每封复用前台读取 API：重复认证并争用前台通道，影响阅读与写标记。
- 复用后台只读会话与现有正文事务（采用）：从数据库查询缺失/旧版正文，
  有界下载并持久保存，重启后自然恢复；前台通道独立保留。

## 本轮决策与实现

1. 受支持的文字与原始 HTML 正文持久写入 SQLite，不写外置正文缓存文件、不按缓存过期清理。
   原始 HTML 不直接经过 IPC，只提供经既有清洗和沙箱约束的展示结果。
2. 后台完整同步包含正文补齐；数据库仍有当前版本正文待办时不能报告完整周期完成。
   缺失正文与已有摘要、旧版纯文本记录都能逐批补齐；已保存当前版正文不重复下载。
3. 图片/附件二进制仍采用既有内容寻址文件与数据库引用；缺少图片缓存时降级图片而保留文字/HTML。
   后台不自动访问 HTML 外部图片，既有图片展示授权不变。
4. 复用现有 schema v3，不新增依赖、字段或迁移。`Cached` 既有 API 字段仅表示本地正文已具备，
   不是“正文只在内存/临时文件里”的含义，不为术语变更破坏 IPC。
5. 保留 BODY.PEEK、时间/数量/字节预算、错误与取消边界。下载受现有
   MIME literal 40 MiB、解码文字总量 1 MiB、单附件 25 MiB 等限制，超限明确失败，不截断后宣称完整保存。
6. 这不是永久归档/备份功能：保留已有服务器删除与 UIDVALIDITY 重建语义；
   只有 UID 清单确认消失才核对对应实例，不把未知正文获取失败当成远端删除。

## 对历史 ADR 的关系

ADR-0002 的 SQLite + 大附件外置架构继续成立；其“超过 1 MiB 正文外置”是历史目标，
当前既有实现尚无该正文外置路径，本轮也不新增。正文始终入数据库；如需支持更大的正文，
应单独确认数据库约束/迁移、安全预算和性能影响，不能悄悄降低保护或改存文件。

## 后果与验证边界

- 首次历史补齐增加流量、数据库与附件目录占用，可能持续多个后台批次。
- 已保存正文无需凭据或网络即可读取；图片缓存丢失不应令文字不可读。
- 网络、格式、大小或存储失败会保留未完成状态，不伪装同步成功；异常邮件/服务商兼容性需继续排查。
- 本地持久性不等于静态加密、无限空间、断电零丢失或永久保留远端已删除邮件。
- 实际测试和服务商观察以任务记录为准；本草稿等待评审，不伪造架构负责人批准。

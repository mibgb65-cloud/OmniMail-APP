# ADR-0006 国际化框架：i18next + react-i18next

> 状态：已生效 | 最后更新：2026-10-24
> 决策：用户确认方案，@Codex 实施
> 相关：[国际化开发约定](../../04-development/internationalization.md) · [产品需求](../../01-product/requirements.md#71-国际化验收标准)

## 背景

现有桌面骨架已将中英文文案按命名空间拆为 JSON，但使用自研 Context 与对象索引读取翻译。用户要求接入成熟 i18n 框架，并已确认新增依赖。迁移必须保留离线启动、类型检查、语言选择及现有本地偏好，不能修改 Go 绑定或顺带改写产品文案。

## 备选方案

### 方案 A：继续维护自研 Context

- 优点：无新增依赖，现有静态文案成本低。
- 缺点：插值、复数和回退需要继续扩展自制引擎，不符合本次接入成熟框架的需求。

### 方案 B：i18next + react-i18next

- 优点：复用现有 JSON 和命名空间，原生支持插值、复数、回退及 TypeScript 资源类型；官方 React Hook 负责语言订阅。
- 缺点：增加运行时依赖和打包体积，需维护框架版本与语言包契约测试。

### 方案 C：FormatJS / react-intl

- 优点：基于 ICU 消息格式，适合复杂消息编排。
- 缺点：现有 JSON 和 Hook 需要调整为消息描述符/ICU 格式；当前界面不需要承担这一迁移成本。

## 决策

选择**方案 B**：

1. 固定依赖版本，经 `createInstance()` 为每个 Provider 创建独立实例；资源复制后同步初始化，不共享可变资源，不注册全局默认实例。
2. 使用官方 `I18nextProvider` 和 `useTranslation`。保留项目同名 Hook 作为兼容适配，提供 `t`、派生 `locale` 和受校验的 `setLocale`，不自行实现翻译解析。
3. 静态导入资源，不配置联网加载器或检测插件；保留既有系统检测、白名单与 `omnimail.locale`。只有手动切换才持久化。
4. 中文作为资源类型基准与回退语言；启用严格键检查，拒绝空翻译。插值由 React 文本节点转义，不开放翻译 HTML 渲染。

## 后果

- 正面：不改业务组件或存储格式即可迁移；框架负责消息能力，测试覆盖类型、切换、回退、复数和安全渲染。
- 负面：生产 JS gzip 增加约 16.51 kB；依赖许可证、维护情况与完整体积评估见开发约定。
- 边界：当前 Context 并非第二套翻译引擎，只暴露语言控制；不翻译邮件正文、后端诊断或版本数据。
- 重新评估条件：实际出现多窗口偏好实时同步、路由资源懒加载、翻译平台接入或富文本消息需求时，单独评审，不默认追加插件。
